# Shelflet deep research expansion

## Executive assessment

Your plan is technically sound, and the core interaction is a good fit for native AppKit rather than a SwiftUI-first architecture. Apple’s macOS drag-and-drop stack is built around `NSDraggingSource`, `NSDraggingDestination`, `NSDraggingSession`, `NSDraggingInfo`, and pasteboard-backed transfer objects, while the windowing behaviors you need for a lightweight utility—nonactivating panels, custom window levels, and collection behaviors for Spaces, full screen, and Stage Manager—are exposed directly in AppKit. A pure SwiftUI shell is still useful for preferences and menu commands, but the shelf itself, the edge hot zone, and drag export/import should be AppKit-owned surfaces. citeturn11search16turn1search0turn1search1turn23search1turn5search2

The biggest missing decisions in the current spec are not feature ideas; they are architectural constraints. The most important ones are: a minimum supported macOS version, a two-window design instead of a single do-everything panel, a notch/Stage Manager-aware screen-placement model, a stricter file-promise materialization pipeline, and a distribution decision made early enough to avoid reworking file access later. Those decisions affect nearly every implementation detail more than shelf visuals do. citeturn33search0turn5search1turn1search12turn5search2turn18search12turn31search10

A practical version floor is **macOS 13 Ventura**. That gives you `SMAppService.mainApp` for modern launch-at-login, `canJoinAllApplications` for overlay-style windows in Stage Manager and full-screen contexts, and current AppKit drag APIs without legacy fallback paths. If you need to support older releases, you can do it, but you will add branching for login-item behavior and window-collection behavior for marginal product benefit in a utility app. citeturn33search0turn33search2turn5search1

## Recommended architecture

The app should be split into four layers. First, an **agent-style app shell** using `LSUIElement` so the app behaves like a background utility and doesn’t live in the Dock by default. Second, a **status-item controller** built with `NSStatusItem`, because that is the native menu-bar utility surface. Third, a **windowing layer** with one set of invisible edge-destination windows and one visible shelf panel. Fourth, a **drag/persistence core** that owns pasteboard reading, promise materialization, bookmark resolution, thumbnail generation, and serialization. Apple documents `LSUIElement` as the key for agent apps that run in the background and don’t appear in the Dock, and `NSStatusItem` as the standard menu-bar element created by `NSStatusBar`. citeturn13search2turn1search2

I would keep the UI mix deliberately asymmetric: **AppKit for the shelf, SwiftUI for settings**. This lets you use AppKit-only behavior where it matters most while still shipping a modern preferences window quickly. SwiftUI is perfectly fine for a settings scene and menu commands, but the shelf panel needs explicit control over focus, activation, drag lifecycles, screen geometry, and collection behaviors that are more direct in AppKit. citeturn12search24turn23search1turn5search2

For the shelf contents themselves, use an `NSCollectionView`, not a custom `NSView` grid and not a SwiftUI `LazyVStack`. Apple’s `NSCollectionViewDelegate` is explicitly intended to manage selection, highlighting, and drag-and-drop support, and `NSCollectionView` already handles insert/delete/move animations and layout updates cleanly. That lines up almost exactly with your requirements for multi-select, grouped drag-out, selection shortcuts, and future layout changes. citeturn30search3turn30search16turn30search1

For icons and previews, use **Quick Look Thumbnailing** first and fall back to standard file icons only when thumbnail generation fails or would be wasteful. `QLThumbnailGenerator` is purpose-built to generate file thumbnails asynchronously, which is exactly the workload a shelf utility has. That is a better fit than inventing your own thumbnail cache pipeline from scratch. citeturn12search6turn12search14

One subtle product risk worth addressing now: an `NSStatusItem` is not guaranteed to be visible all the time because menu-bar space is limited. Apple’s docs explicitly warn to use status items sparingly and note that they may be unavailable due to insufficient space. That means the status icon should not be your *only* recovery path. Ship a standard “Show Shelf” command, a first-run onboarding hint, and an optional “Show Dock icon” troubleshooting switch even if Dock mode is not a first-class mode. citeturn12search0turn12search8

## Drag and drop pipeline

The intake pipeline should be formalized as a state machine rather than a handful of callbacks. AppKit’s destination flow is: the destination registers accepted dragged types, `draggingEntered(_:)` fires when a dragged image enters the destination bounds, `draggingUpdated(_:)` fires repeatedly as the cursor moves, `prepareForDragOperation(_:)` is the last pre-drop acceptance point when the user releases, and `performDragOperation(_:)` is where you actually import the pasteboard data. Apple also notes that you should usually examine the pasteboard in `draggingEntered(_:)`, not `draggingUpdated(_:)`, because `draggingUpdated(_:)` is invoked multiple times. citeturn22search0turn32search17turn27search2turn32search21turn32search15

That leads to a clean intake design: when `draggingEntered(_:)` fires, classify the payload once into one of four buckets—file URLs, folders/packages, file promises, or unsupported—and cache that classification on the drag sequence number. Then use `draggingUpdated(_:)` only to drive hover affordances and operation masks. This avoids reparsing the pasteboard on every mouse move, keeps reveal latency down, and makes it much easier to log why a drag was rejected when debugging creative-app compatibility. Apple’s drag docs also say the destination should evaluate the overlap between the source’s allowed operations and the destination’s accepted operations when deciding what to return. citeturn32search6turn27search2turn32search17

For concrete files, prefer `NSPasteboard.canReadObject(forClasses:options:)` and `readObjects(forClasses:options:)` with `URL.self`, refined by Uniform Type Identifiers where appropriate. Apple documents `UTType.fileURL` as `public.file-url`, and the pasteboard APIs explicitly support filtering URL reads by content conformance. In practice, that means you can accept file-system URLs without accidentally treating arbitrary web URLs or text as shelf items. citeturn3search2turn3search8turn3search11turn1search6

File promises are the most important “do this early” feature in your plan, and your current spec is right to treat them as first-class. Apple’s file promise guidance and samples make three relevant points: `NSFilePromiseReceiver` is how a destination receives promises from the pasteboard; `receivePromisedFiles(atDestination:options:operationQueue:reader:)` is the API that materializes them; and file promises are different from URLs because they can be read and written asynchronously later on a background queue. That means Shelflet should **always** materialize accepted promises into its own cache directory before displaying them as normal shelf items. It should not try to keep them in a half-real, half-not-yet-written state longer than necessary. citeturn18search14turn3search10turn22search6turn18search12turn0search20

On drag export, the shelf should usually re-export **real file URLs**, not fresh promises. Once a promised file has been materialized into your cache, the simplest and most compatible behavior is to drag out the cached file URL. AppKit starts a new drag with `beginDraggingSession(with:event:source:)`; that call returns immediately and the drag actually begins on the next run-loop turn. Apple also provides `shouldDelayWindowOrdering(for:)`, specifically to let a drag begin without activating the app or bringing the window forward in a way that could obscure the destination, and `draggingSession(_:sourceOperationMaskFor:)` to declare which operations the source allows. Those are the exact hooks you need to preserve normal copy/move/link expectations while keeping Shelflet visually out of the way. citeturn1search1turn11search1turn1search9turn2search2turn27search1turn11search5

One improvement to your semantics section: represent the end of a drag-out as **three separate outcomes** in code—dropped and accepted, cancelled, and dropped but destination-side failure/ignore—rather than a single “successful drag.” AppKit’s source operation APIs tell you what was allowed; they do not make the shelf omniscient about whether the destination finally copied or moved every underlying byte the user expected. Your instinct to treat shelf removal as UI cleanup rather than proof of a physical move is exactly right, and it should be encoded in the model layer as policy, not inferred from visual behavior. citeturn27search0turn27search1turn32search6

## Windowing and interaction model

The shelf should not be one magical window that is sometimes invisible, sometimes a hot zone, and sometimes interactive content. Use **two distinct surfaces**: an ultra-thin edge destination window and a separate shelf panel. Windows and views in AppKit define rectangular regions for drawing and event handling, and AppKit gives both views and windows direct APIs to register dragged types. Splitting the surfaces lets you keep the hot-zone logic tiny and conservative, and it avoids a common failure mode where the same window that must be easy to drag onto also steals clicks or activation at the wrong time. citeturn22search1turn22search0turn22search2

For the visible shelf, use `NSPanel` with the `.nonactivatingPanel` style mask as the default starting point. Apple documents that style specifically as a panel that does not activate the owning app. If you want keyboard navigation only after explicit focus or click, `becomesKeyOnlyIfNeeded` gives you a better middle ground than either “always key” or “never key,” and `isFloatingPanel` can be turned on only if testing shows the shelf gets lost too easily behind working windows. Apple also notes that panels do not float by default. citeturn23search1turn24search1turn24search2turn0search1

Spaces, full screen, and Stage Manager deserve more precision than your current spec gives them. `NSWindow.CollectionBehavior` is the switchboard for all of this. `canJoinAllSpaces` makes a window appear in all Spaces; `fullScreenAuxiliary` makes it display on the same Space as a full-screen window; and on macOS 13 and later, `canJoinAllApplications` is explicitly meant for floating windows and system overlays that should join other apps’ full-screen spaces without participating in Stage Manager layout. The safest plan is to treat this as a compatibility matrix: use `canJoinAllApplications` for the thin hot-zone overlay where supported, pair the visible shelf with `fullScreenAuxiliary` where needed, and test carefully because Stage Manager behaviors are not just cosmetic. citeturn5search2turn5search4turn5search0turn5search1turn5search7

Your screen-positioning model also needs one important refinement: **do not choose a target screen by asking for `NSScreen.main`**. Apple defines that as the screen containing the window with keyboard focus, which is not necessarily where the current drag is happening. Use the hot-zone window’s owning screen, or derive placement from the drag location relative to the destination window. Rebuild screen bindings whenever display config changes, because Apple says the screens array should not be cached and that screen changes post `didChangeScreenParametersNotification`. citeturn1search4turn32search0turn32search3turn28search5turn28search1

Top-edge support also needs to be **notch-aware**. Apple’s `visibleFrame` excludes the dock and menu bar and, on Macs with a camera housing, does not include the bezel or the visible areas on either side of it; those side areas are exposed separately through `auxiliaryTopLeftArea` and `auxiliaryTopRightArea`. In other words, a naïve “full-width top strip” is wrong on notched MacBooks. If you implement a top-edge trigger, compute it from `visibleFrame` first and then optionally stitch in the auxiliary top areas rather than spanning the physical frame as if the notch did not exist. citeturn12search4turn1search12turn21search20

For the shelf’s visual treatment, use standard semantic materials through `NSVisualEffectView`, not a custom blur stack and not a showy glass imitation. Apple’s docs say to choose materials based on intended use rather than perceived color, and the current HIG guidance warns against overusing Liquid Glass in the content layer. For Shelflet, a restrained standard material is more aligned with the product concept than a highly reflective or attention-seeking surface. citeturn9search0turn12search15turn29search5

## Persistence, sandboxing, and distribution

Your reference-vs-cache model is the right backbone, but it needs to be made more operational. In a sandboxed app, the container is the place where you have unrestricted read/write access, and Apple explicitly recommends security-scoped bookmarks when the app needs to access a user resource again after exit and relaunch. That creates a clean rule set for Shelflet: **referenced items** keep a bookmark plus display metadata; **cached items** live in the app container and are owned by your cleanup policy; and **promises always become cached items** once materialized. citeturn17search13turn11search22turn17search0turn17search14turn17search20

The bookmark lifecycle in the spec should be expanded from “store bookmark data” to a specific workflow: create with `withSecurityScope`, resolve with security-scope options when needed, detect the stale-bookmark flag on resolution, rewrite stale bookmarks immediately, call `startAccessingSecurityScopedResource()` only around actual work, and always balance it with `stopAccessingSecurityScopedResource()`. Apple is very explicit that security-scoped bookmarks are for persistent access across launches rather than for every transient file interaction. citeturn17search1turn17search2turn17search11

The distribution decision matters more than it may look. Apple requires App Sandbox for Mac App Store distribution, but for direct distribution with Developer ID and notarization, hardened runtime is required while App Sandbox is optional. That means you have two valid product paths. If the goal is Mac App Store distribution, build sandbox-first now and keep the bookmark/cache layer central. If the goal is a faster direct-distribution MVP, you can ship outside the App Store with notarization and hardened runtime and defer some sandbox friction—while still keeping the internal storage model App-Store-friendly later. citeturn31search10turn31search0turn31search8

For entitlements, keep the surface area narrow. The relevant baseline is App Sandbox plus user-selected file access, and Apple documents `com.apple.security.files.user-selected.read-only` and `com.apple.security.files.user-selected.read-write` under the file-access entitlements. Your MVP does **not** need Accessibility, Input Monitoring, USB, camera, or broad file-system access, and broad permissions would make both review and user trust harder. citeturn26search3turn26search1turn26search4

Launch at login is straightforward on modern macOS: use `SMAppService.mainApp`, register and unregister through `SMAppService`, and surface status cleanly in settings. Apple documents that `register()` starts a login-item service subject to user approval, and the `.requiresApproval` status means the user needs to take action in System Settings. In practice, that means your settings UI should not just show a toggle; it should also show current state and a help link explaining where approval lives if the toggle cannot fully complete autonomously. citeturn33search0turn33search2turn33search10turn14search6

## Delivery plan and open questions

A stronger build plan is to front-load **risk retirement** even more aggressively than your current phase list. First, ship the edge-destination spike and certify that a thin destination window can accept Finder files, browser downloads, and at least one creative-app promise source without breaking normal edge clicks. Second, add the visible shelf as an `NSPanel` backed by `NSCollectionView`, but still with in-memory items only. Third, add the full intake matrix for URLs and `NSFilePromiseReceiver`. Fourth, add persistence, bookmarks, and cache cleanup. Only after those pass should you spend time on animation polish, Quick Look, or any “delight” layer. That ordering follows the actual platform risk profile Apple’s APIs imply: drag destination mechanics and promise materialization are the hard parts; menu-bar chrome is the easy part. citeturn22search9turn18search12turn17search0turn30search3

The MVP ship gate should be tightened slightly beyond the current wording. I would not call it done until you can demonstrate all of the following in recorded QA runs: Finder file URL intake; one promise-based source app from Apple’s documented examples such as Mail, Safari, or Photos; drag-out into Finder; drag-out into one non-Finder document target; relaunch with both a valid bookmark-backed reference and a valid cached promise-backed item; and correct behavior when display configuration changes mid-session. Those are the flows most directly tied to the APIs Apple documents for drag destinations, file promises, bookmarks, and dynamic screen configuration. citeturn0search4turn18search12turn17search0turn28search5

The main open question is **sandbox behavior for drag-arrived external file references across app relaunch**. Apple’s reviewed sandbox material is explicit about open/save panels and security-scoped bookmarks, and it is explicit that bookmarks are needed for cross-launch persistence, but the snippets reviewed here do not spell out every edge case of cross-process drag-arrived permissions in the same way. That is not a reason to abandon sandboxing; it is a reason to treat “drag in file, relaunch, still readable through stored bookmark” as an explicit pass/fail certification item early in development. citeturn11search3turn17search0turn26search0

The second open question is **how aggressive the hot-zone window can be without becoming annoying**. Apple gives you the window-level and collection-behavior tools, but it does not hand you an ideal UX recipe for “transparent drag target along a screen edge.” You will need empirical tuning of thickness, level, peeking delay, and screen-mode behavior, especially with full-screen apps and Stage Manager. citeturn2search10turn2search3turn5search2turn5search1

The third open question is **certification breadth for file promises**. Apple’s own sample materials mention apps such as Mail, Safari, and Photos, but real-world creative tools may serialize promise metadata differently enough that you should maintain an internal compatibility matrix rather than assuming one passing promise source proves them all. citeturn0search4turn18search12

Overall, your plan is already pointed in the right direction. The best expansion is not “more features”; it is a more opinionated technical contract: AppKit shell, two-window topology, `NSCollectionView` shelf, promise-to-cache intake, bookmark-backed references, notch-aware geometry, and an explicit distribution choice. If you lock those in, Shelflet stops being “a clever concept doc” and becomes a buildable macOS utility with a realistic path to a polished MVP. citeturn11search16turn30search3turn18search12turn17search0turn1search12turn31search10
